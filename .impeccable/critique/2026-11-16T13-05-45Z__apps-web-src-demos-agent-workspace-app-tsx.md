# 财小智产品、交互与竞品评估

评估日期：2026-11-16。评估方式：两路独立评估（A：/root/design_review；B：/root/technical_review），加主代理核心流程检查及独立竞品研究。

**判断：财小智已有清晰的财务 Agent 产品骨架，下一步最有价值的投入是让结果准确、事项持续存在、证据可核对、办理可恢复。建议先修业务可信度，再补三类用户的工作闭环，最后统一交互细节。**

范围：实际浏览首页、会话、材料核对、智能提单、预审、规则、技能与工具、数据分析、制度及历史入口；检查1440×900与1280×800桌面尺寸；只读核对相关源码、正式工程接口及8家竞品官方资料。未修改产品代码，未提交真实业务；没有登录竞品账号实测，官网能力不等于独立验证的效果。新agent.html仍主要是本地原型，不能将仓库其他正式入口的API/Worker能力算作它已接入。

## 值得保留

1. 对话首页克制，输入、能力与示例有主次，使用指引默认收起。
2. 智能提单在右侧完成，区分概览与编辑、草稿与提交快照；修改后旧检查失效。这些基础符合财务操作需要。
3. 预审区分需关注、待核实、未发现异常；分析已有口径、来源、比较期和明细；技能已有版本、权限与仅存储状态。应把这些现有能力连起来，而非重复建设。

## 五项优先改进

### 1. P1：结果必须严格回应用户指定的条件和对象

浏览器实测输入“分析2026年8月研发部费用”后，页面部门变成研发部，期间仍是2026年10月，给出12.00万元完整分析，未提示8月未支持，原查询还被清空。源码analytics-model.ts:325仅识别9月和10月，normalizeAnalysisScope也回落到10月。

制度追问同样存在错配：Supporting.tsx:177无论从哪份制度进入，都发送“上海出差的住宿标准是多少？”，App.tsx:445的knowledge分支固定引用差旅制度。该结果链由代码确认，未实际发送问题。

建议：保留用户原问题，显式展示实际执行的期间、组织、币种与对象；不支持的条件不能静默替换。制度追问保留当前制度ID、版本和条款，先准备可编辑问题，再按所选对象查询。查不到时明确无结果。

验收：8月无数据就告知8月无数据；从招待制度提问不能固定转成差旅住宿。主管读取汇总前不应承担识别系统偷换条件的责任。

### 2. P1：统一制度、规则、金额与适用范围的财务口径

Supporting.tsx:30写“每人每晚600元”，R002及SubmissionWorkspace.tsx:160、189按金额除以房间数×晚数执行“每间夜600元”。两人合住一间一晚900元时，两种口径会得出不同结论；这是依据代码的示例推演，未浏览器实测。城市、职级条件也没有完整进入此原型的规则选择。

建议先由业务确定口径，再统一制度文本、规则解析、算法和结果解释，涵盖城市、人员范围、币种、生效日期、计量单位及例外审批。规则编辑除版本差异外，应增加正例、反例、临界值和受影响单据预览。

多币种已按原币分组汇总，不应误判为直接相加。当前缺口是换算依据与规则核验：默认住宿规则下，外币住宿会进入待核实并阻止继续，却泛化提示缺少住宿单价。应明确需要汇率依据或人工处理，而非让用户反复补一个已有的金额。

### 3. P1：从每类一个草稿，升级为可靠的多事项办理

submission-state.ts:14、31将草稿固定为travel、expense、personal三个槽，页面首次显示三个空草稿。它能演示三种类型，难以表达上海和北京两笔差旅同时独立办理。首页未发送草稿刷新后消失已实际复现；整个工作空间localStorage保存失败被空catch忽略，跨标签旧状态覆盖为静态确认风险，未破坏用户存储做故障注入。

建议：每个事项与单据有独立ID，会话只是入口；只有用户实际开始时创建草稿。首页文字、能力、引用与附件关联自动保存，显示真实保存状态；多标签冲突能够识别。一次出差关联申请、实际行程、材料、报销和回执，关闭抽屉、换会话或刷新后继续同一对象。

验收：同时办理两笔差旅，切换会话和刷新后内容不串；首页长需求可恢复；保存失败可重试并保留内容。历史页面增加待我补充、待我确认等筛选即可，不需要把首页变成待办门户。

### 4. P1：把证据核对、执行状态和真实回执接成闭环

已观察材料核对展开后主要显示文件名和可改字段，预审单据信息中“关联材料”只写“已关联”。用户能看到判断，却仍难验证判断依据。源码还确认：来源重试500ms后本地置ready；提交只创建本地REQ并设为待回执，查询回执只更新时间。这些不是已经对外发起的请求，不能让用户等待一个不会到来的业务回执。

建议：证据定位到附件页、原值和相关条款；人工修改显示旧值、新值及哪些检查失效。状态清楚区分本地保存、尚未发送、已发送待受理、结果待确认、待审批、已支付。未知结果先查原请求，不重复提交；等待时显示谁处理、卡在哪、可做什么。回单查询、翻译、合同分析在选择前标明未接入，保持必要状态简短就近。

仓库已存在正式ActionService、Run恢复/取消、知识引用及权限接口，应复用这些基础，而非再写一套前端状态。尚未验收真实服务、SSO/OA/OCR、数据库或模型，不将现有源码当作生产接入证明。

### 5. P2：统一模块交互，并围绕三类角色的决策组织信息

同屏外层为林悦、内嵌工具为林晓且可切换，是已观察的身份表达割裂；未验证真实越权。上传技能实际仍用624px右抽屉，与已确认的居中弹窗约定不一致。从技能目录选择技能会创建空会话，首页就近选择则只改草稿。应统一动作结果、身份及权限状态；正式接入前身份授权整合属于发布门槛。

| 角色 | 首要任务 | 建议呈现与动作 |
|---|---|---|
| 员工 | 少填字段、一次补齐、知道钱到哪了 | 默认突出待补项与待确认项，自动带入可信字段；退回后定位修改处；可继续同一草稿 |
| 主管 | 判断业务必要性与预算影响 | 业务目的、金额、预算占用、超标原因、待决定事项；提供补充说明或转入正式审批入口 |
| 财务 | 快速验证风险与证据 | 风险优先队列、票单对照、重复票据关联、规则版本、已核实记录、上一单/下一单 |

角色差异放在同一个单据或事项的摘要、可见字段与操作中，权限由服务端决定。主管视角目前比填单和财务预审更薄，优先补决策摘要，无需另建复杂门户。

## 整体交互与视觉

首页的简洁、静态角色形象和少量强调色适合长期办公使用。智能提单继续右侧完成；需边聊边填时允许操作背景；上传技能改为宽居中弹窗；复杂批量审单可以进入专业工作区。技能、工具、规则的管理能力按权限渐进显示。

较小问题：单据查询/单据进展、制度问答/制度知识等名称应建立一致别名与动作表达；内嵌工具统一主题并去除重复指引入口；新增费用在未操作时就呈现多处红色错误，应区分初始缺项与提交校验；报错支持一键定位，费用多时提供分组和待补项导航；技能选择不应产生空会话。继续保持页头无教学段落、使用指引默认收起。

认知负担主要来自跨模块身份和对象变化、需人工记忆的证据与状态，而非单纯首页按钮数量。情绪低点是看起来成功但条件未执行，以及看似保存却不能恢复；最有效的信任提升是准确的阶段、可核对的证据和可恢复的工作。

## 建议实施顺序与验收

第一轮修正确定性问题：8月查询、制度追问绑定、人夜/间夜口径、首页草稿刷新恢复、未发送/待回执状态。对应能力以harden、clarify为主。

第二轮贯通一条真实差旅报销流程：多单据独立保存→材料证据→规则检查→用户确认→正式系统受理→退回补充→重提→回执。接入正式身份、Action/Run和文件服务，并验证超时、未知结果与重复确认。

第三轮提升三类角色效率：员工只补缺项、主管有决策摘要、财务可连续核对；统一技能上传容器和工具外观，最后polish收口。

用首次提交通过率、补充轮数、员工办理时间、财务每单核对时间、退回到重提耗时、未知回执解决率、数据范围错误率衡量效果。它们是建议监测指标，本次没有测量基线，不承诺虚构提升比例。
