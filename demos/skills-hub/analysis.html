产品定位与本轮设计前提

建议定位：企业内部 Skill 资产与分发中心，附带受控的财小智运行入口。一般使用者先判断“能帮我做什么”，作者关心“如何上传与分享”，审核者关心“依据是否充分”，管理员关心“谁可以做什么”。不应让普通员工先理解 Agent 框架、工具注册或安装命令。

一份资产可以被保存、阅读并供获授权者下载；能否在其他环境运行，以该版本声明和验证过的兼容范围为准。经过单独评估后，也可以供财小智调用。统一保存原始包和版本档案，运行适配信息作为附属信息；不把财小智独有的配置强塞进所有上传包。

  • 按内部企业平台设计，默认没有公网匿名市场、付费交易或外部组织共享。
  • 上传首先进入作者工作区，未审核资产仅作者及获派审核人可见。“保存成功”不代表向平台目录公开。
  • 初期建议接受 SKILL.md 与标准 ZIP 技能包。可保存的附件类型、文件大小、压缩层级需评审明确；含脚本的包即使允许入库，也不自动执行。
  • 默认所有对他人发布及所有可在财小智运行的版本均需双审；个人草稿可保存，但不沿用旧设计的“私人校验通过即可直接激活”例外。
  • 默认由发布负责人确认受众后上架；审核通过与立即公开分开。私人运行使用双审通过且仅向本人发布的版本，不进入其他人的目录。
  • 首期以用户主动选择、一次任务一个主 Skill 为默认；自动推荐和多 Skill 编排后置。

以上是为便于评审提出的建议默认值，不代表已经确认的公司制度。

内部产品分析：从能力目录转向资产中心

已核对原 M05《Skills Hub：能力选择、个人创建与共享治理》与关联模块设计。原稿已有版本固定、源码与调用权分离、审核、停用等基础，但主要围绕“可运行能力”组织。这次需求改变了目录的中心。

原设计重点本轮应调整的产品行为前端表现
目录以可使用能力为主可查看的资产即可进入目录，无运行权仍可合法阅读或下载目录筛选“全部 / 可在财小智运行 / 仅存储”，避免只显示一个“使用”按钮
单一共享审核业务、技术分别记录结论，技术内再分安全与兼容两条审核轨迹，展示版本、审核人、意见和范围
use 与 source_read 分离增加独立下载动作，澄清档案可见与源码阅读区别权限摘要显示“可看说明 / 可下载包 / 可在对话运行”
manifest、Markdown、JSON支持资产包、附件、来源、适用环境、版本说明上传向导、文件清单、下载物说明、来源与负责人
私人版本校验后激活建议私人运行也走审核，私人存储可自由保留“保存草稿”“提交审核”与“申请运行接入”三个含义分明
版本固定与停用机制保留；更新只影响后续新任务，撤权在执行前复核历史结果仍标旧版本；不可用时解释原因，不静默换 Skill
相关模块承担的用户价值边界
Skills Hub找技能、看说明、下载、维护、审核与授权不因上传自动注册新工具
对话主界面选择技能、补齐任务信息、查看进度和结果不把所有上架资产都放进可运行选择器
身份与组织权限解析人员、用户组、部门与授权范围技能作者的身份不能传给调用者
业务系统与能力目录提供被允许的数据和工具Skill 调用权不授予业务数据权
运行与确认中心固定版本、恢复任务、核实业务操作结果不能把技能审核通过当成单据审批通过

现有前端不作为视觉基线；本轮只沿用适用的业务边界。dsh、LangGraph 或其他执行框架的差异，集中在运行适配和状态回传，不应改变用户对“已保存、已发布、可运行”的理解。

可形成差异化的三个产品点

  • 业务证据可读：不是只有“审核通过”绿标，而是能看到适用任务、案例、输出标准与双审责任。
  • 运行资格可解释：明确“仅存储”“待适配”“缺少业务权限”“依赖异常”，避免全部变成灰色的“不可用”。
  • 分发与运行独立：可供员工在其他环境下载使用，也允许受控运行但不开放技能包下载。

上述差异化是基于需求与公开证据的设计推导，不是对竞品功能缺失的绝对判断。未引用 Claude 平台总览中与专项组织管理文档冲突的旧限制。

技能卡片必须在几秒内回答

  1. 这能帮我完成什么任务？
  2. 产出是什么，有没有示例？
  3. 来源是谁，当前是否已审核上架？
  4. 能否在财小智运行，还是只供下载？
  5. 我下一步能点什么？

详情页的信息顺序

  1. 名称、用途、状态、负责人、主要操作
  2. 输入、产出、适用范围、结果预览
  3. 当前版本、业务审核、技术审核
  4. 所需能力与业务权限摘要
  5. 文件/版本/源码：按权限展开

视觉建议：明亮办公环境下的白纸底色、墨绿主操作、低干扰分隔线、清晰中文层级。身份与权限用文字辅助颜色；状态不只靠绿点；列表金额与版本对齐。桌面优先让重要信息同屏，窄屏将侧栏折叠、详情转为单列。

前台卡片只突出“已上架”和“可运行/仅存储”两个核心标签，完整状态在详情和管理端展开，避免一张卡塞满五种进度。业务、技术可以并行审核，同一版本两者通过才进入待发布。技术结论可为“通过（仅分发）”，并另记“运行兼容未通过”：这时可按仅存储模式发布，运行授权强制关闭。安全审查退回的版本不能沿用此路径上架。

业务审查关注

  • 使用场景与适用人群是否准确
  • 依据、口径、时效和术语是否合理
  • 输入不完整时是否追问或拒绝
  • 输出是否有来源、边界和验收样例
  • 是否可能误导用户把建议当正式审批

技术审查关注

  • 结构、文件类型、敏感内容与潜在恶意行为
  • 外联、脚本、依赖、工具和数据范围
  • 在目标环境的兼容性与试运行证据
  • 超时、缺权、失败与恢复是否可控
  • 来源、许可证声明与版本可追溯性

扫描结果是审核证据的一部分，不能宣传为绝对安全保证。审核人只获该次审核所需的内容访问；作者不得批准本人版本；退回需给可执行的修改理由。改包、新增依赖或扩大共享范围后，旧结论不能直接沿用。

权限：三种动作，两个“查看”层次

先约定“查看”指看到资产档案与公开说明。源码、文件正文、完整提示词另设内容访问控制，避免“禁止下载、却可全文复制”的误导。首期可把源码阅读与下载包权限绑定，在高级配置中预留分开授权。

示例受众档案可见技能包下载财小智运行典型体验
全体员工允许不允许不允许了解用途；需要时申请对应权限
部门分析人员允许不允许允许运行已审核方法，不开放源码包
技术支持组允许允许不允许下载到其他环境研究或适配
技能维护组允许允许符合运行条件才允许维护内容不意味着运行审核豁免
未获可见权人员不允许不允许不允许搜索、推荐、数量和直达链接均不泄露资产

界面采用用户/用户组逐行授权，三列复选框。下载与运行互不联动；授予任一动作时要求档案可见，并解释依赖。组织组授权取并集，未授权默认拒绝；首期不引入复杂的显式拒绝优先级。收窄授权可立即生效，扩大受众形成审核变更；保存前展示变化摘要。

实际可运行 = 有效发布版本（范围可仅本人） ∩ 双审通过 ∩ 财小智兼容通过 ∩ 当前用户调用权 ∩ 当前业务数据/工具权限 ∩ 依赖可用

已授权用户可以申请下载或调用权限；不可见资产不提供“透露名称”的申请入口。申请应交给资源授权负责人，不能作者随意越过其组织管理范围。撤权会阻止后续在线下载/调用，已经下载到本地的文件不能承诺远程收回。调用不下载也不能保证用户永远无法从模型输出推测提示内容，因此秘密不应写入 Skill。

对话交互：先选择，再表达任务

  1. 选择器：输入框旁“选择技能”，支持名称与场景搜索，默认只展示已上架、可运行、有调用权的版本。可见但不可用的资产从“查看不可用原因”进入，保持正常选择列表简洁。
  2. 选中：输入区出现“月度费用分析 · v1.2”标签，可移除。选择和进入聊天都不自动发送消息、不开始执行。
  3. 任务准备：用户输入目标；缺月份、部门、附件等必要信息时，在对话内给紧凑表单。业务范围只能从已授权对象选择。
  4. 开始运行：发送时重新校验权限和版本，固定本次运行版本。进度用“读取数据、生成分析、整理报告”等可理解步骤；演示页面明确显示模拟。
  5. 结果：展示报告/表格/下载产物，附此次 Skill 名称版本、数据范围、来源和完成状态。技能包下载权不控制报告等运行产物；报告导出仍按所属业务数据导出权限校验。不能只有一大段聊天文字，也不能虚构数据来源。
  6. 继续：普通追问可针对已有结果；若开始新任务或更换 Skill，重新选择与校验。旧结果仍标原版本，运行中不热切换。

不建议首期把全部 Skill 永久装到每个会话里。显式选择便于初期业务评审理解“本次用了哪种方法”，也使责任、版本和权限更清晰；自动推荐可在积累真实使用数据后补充。

异常、更新与停用必须有可理解的结果

场景用户看到的状态下一步
仅存储，尚未适配“可按权限下载；暂不能在财小智运行”有下载权则下载；作者可申请适配
有调用权但缺业务数据权“你暂无法访问该任务需要的数据范围”改选授权范围或按业务系统流程申请，不暴露受限数据
一审通过、另一审退回分别显示审核意见，本次版本不可发布；既有已发布版本不受影响作者创建修订版本，重提需要核验的审核
新版本待审已发布 v1 与待审 v2 并列普通使用者继续使用 v1；审核者查看 v2 差异

首期范围与可行性判断

优先级建议范围评审关注
首期必须上传/档案/版本、目录和详情、双审与退回、独立三权、仅存储与可运行状态、聊天主动选择、停用四项核心需求形成闭环，服务端权限与文件访问须同时落地
首期可简化一个固定双审流程；少量经过适配的运行技能；单主 Skill；用户组授权；手工提交测试证据不需要一开始做可视化审核流程编排或自动适配所有外部包
后续增强自动推荐、批量导入、依赖自动分析、版本差异强化、自动化评测、受限试用、跨组织分发基于真实上传量、使用率、审查负担决定
本轮不建设任意脚本执行平台、通用插件市场、付费交易、多 Skill 自主编排、Agent 框架选型避免把交互评审扩大为底层工程重建

可行性结论：目录、上传、版本、审核和授权是常规企业资产管理能力；真正需要提前做技术验证的是：如何把已评估技能交给不同运行框架、执行前如何复核身份与工具权限、停用如何影响等待中的任务。这些问题应验证，但不妨碍先完成前端评审。

建议对外保持“技能档案、审核结论、授权动作、运行状态”四组稳定数据。运行适配层对接 dsh 或其他框架。先用一项报告类只读技能完成端到端样板，避免以“兼容 Agent Skills 标准”替代实际试运行。

验收指标应从可观测行为起步：用户是否能区分存储与运行、找技能需要几步、缺权原因是否看得懂、退回意见是否可修改、发布前能否准确复述受众。后续再记录审核耗时、退回原因、有效复用率与运行失败原因；不靠下载量给安全性排名。

进入开发前，需要收敛的产品决策

  1. 允许保存什么：只接受规范包，还是也允许保存待整理的不规范包？建议后者留在私人草稿，不进入公开目录。
  2. 查看到哪一层：档案、说明与源码分开；首期建议源码阅读随下载权开放。
  3. 谁来审：业务负责人和技术负责人如何按分类分配，是否允许同一人兼任？建议两个独立责任人，作者不得兼审自己的提交。
  4. 何时重新审核：内容、依赖或受众扩大需重核；仅收窄授权可直接生效。纯展示文案可另定轻量流程。
  5. 私人技能能否运行：本稿默认也需双审，不因私人存储免除运行要求。
  6. 申请权限走哪里：接已有组织权限流程还是 Hub 内审批？原型只展示入口和状态，不预设现有系统已具备。
  7. 如何评价存储价值：下载复用、维护频率、资料完整度应单独衡量，不因没有财小智调用量被视为无效资产。

建议评审先确定上述业务口径与页面行为，再选一个只读分析 Skill 验证运行接入。这样可以在不绑定 Agent 框架的前提下推进产品。
