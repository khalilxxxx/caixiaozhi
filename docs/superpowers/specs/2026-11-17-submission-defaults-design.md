# 智能提单默认规则与场景优化

## 目标与本轮选择

用户只说明出差目的地、日期与目的时，先保存草稿并补齐可用默认值。员工档案和线路参考能判断的起点、交通与席别直接采用，不要求用户重复确认；仅对无法默认的缺失行程信息追问。收集结束后展示可核对草稿卡，完整编辑、校验和提交保留在现有右侧抽屉。用户明确指定、修改或清空的字段优先。

本轮直接落实用户提出的优化：采用服务端确定性默认规则、模型理解自然语言、前端展示结果与来源的组合。仅改提示词无法保障人工清空、重排和依赖重算；将所有字段交给模型猜测则无法保证来源一致。沿用现有 Agno/Python 与 React/TypeScript，不新增外部接口或依赖。

## 默认规则

| 场景 | 自动处理 | 不适用或缺少依据 |
| --- | --- | --- |
| 身份组织 | 当前匹配员工档案提供申请人、默认部门、付款公司；普通差旅为默认类型 | 陌生申请人不继承林悦的组织或常驻地；没有权限目录不声称完成授权核验 |
| 只说目的地 | 首段缺出发城市时采用员工常驻地 | 用户明确从其他城市走时保留；档案无 Base 时询问起点 |
| 连续多城市 | 后段缺起点时承接上一段终点；默认值随依赖更新 | 明确起点不覆盖，衔接冲突留给校验 |
| 明确返回 | 已明确为返程的行程缺终点时回实际首段起点；返程未定时保存 `returnDatePending`，生成或保留一条稳定 ID 的待补回程，城市衔接实际行程、交通采用可用推荐、日期留空 | 不将任何最后一段都当返程；明确单程不添加返程，未提返程安排可问一次；已明确未定的返程日期不重复问、不猜 |
| 交通推荐 | 对申请按已知线路距离、铁路时长与可达性选择交通；常用席别二等座/经济舱 | 未知线路不造公里数；明确自驾、席别或跨日安排优先；不拿推荐填报销事实 |
| 到达日期 | 差旅申请出发日有效且未指定到达日时，默认等于该段出发日；不依赖线路距离或时长，不额外追问 | 明确到达日、人工清空、明确跨日或过夜安排保留；报销不根据计划默认补实际日期 |
| 相对日期 | 模型用北京时间当日解释明天、后天、明确的下周星期；已有日期不重解 | “下周去”缺具体日期时只追问日期，不顺便猜周一或返程日 |
| 费用默认 | 延续首次 CNY、适用住宿非租房 | 金额、人数、房间数、OA、派工、同行人和实际交通不猜；人工清空不补回 |

交通参数为本轮可调整的本地建议：已知线路铁路距离不超过 800 公里且参考时间不超过 4 小时优先铁路；长途且有航班参考时推荐飞机。线路均标明本地参考、非实时，不冒充公司制度、实时票价或班次查询。未覆盖线路保留待补。

## 字段保护与交互

- 业务服务维护 `autoFill.fields`（值、标签、规则、来源、依据）与 `autoFill.suppressed`（主动清空）。行程路径使用稳定 ID，增删重排不串字段。
- 人工值优先；依赖变化只更新仍属系统建议的字段。字段被用户改写或清空后，原来源失效。服务端不接受客户端伪造默认依据。
- 模型修改以有效草稿（含尚未保存的编辑）为基线，只更新用户本轮明确的字段；行程集合保留其他行的稳定 ID，避免补返程日期或交通时覆盖去程、同行人及人工内容。变更后旧校验失效，已提交快照不回填。
- 抽屉展示填好的值与简短推荐状态；“自动填写依据”默认收起，仅展开时列出来源、依据。无默认项时不展示空壳说明。
- 仅对无法默认且用户尚未说明暂未确定的缺失行程信息使用追问卡，一次一个问题；已有推荐值、同日到达和已说明的事由不重复问。返程未定状态可保存草稿，但缺失日期仍由提交校验阻断。
- 追问期间后台持续保存草稿、引用与工具成果；`collecting` 消息暂不展示提单卡，其他业务卡及历史已展示卡保留。收集结束转为 `ready`，只展示当前目标草稿卡，并在右侧抽屉编辑、校验和提交。
- 失败、暂停或服务重启保留草稿与引用；有待答问题时继续 `collecting`，无待答问题时展示已存成果供恢复。续办读取当前真实草稿 ID，不重复新建或覆盖旧单。卡片元数据放在独立系统上下文中供续办使用，不混入助手正文或输出内部 JSON、ID。

## 典型体验与验收

1. “明天去上海拜访客户，周五回来”：员工 Base 为杭州时填杭州→上海→杭州，交通按线路推荐，不再确认推荐值；日期按北京时间解析，各段到达日默认等于该段出发日。
2. “这次从北京走”：起点保留北京，返程默认回北京；原自动交通按新线路更新。
3. “去程改一等座，返程还是二等座”：两段分别保留，其他字段不动。
4. 删除交通方式后继续补事由：交通保持空，系统不反复填回；校验只提示仍缺交通。
5. “先上海再苏州”：后段起点承接上海；中间城市改变时只有自动衔接值更新。
6. “下周去上海，返程未定”：起点与交通先采用默认，保存一条日期为空的待补回程，仅追问尚未明确的去程出发日期；回答后出卡，不重复问返程日期，不编造停留天数。
7. 报销火车票但交通信息缺失：不把申请推荐当实际出行，依据材料或由用户补充。
8. 待补回程后说“本周六返回，回程改高铁”：更新原回程 ID 的出发日期和交通，自动补齐同日到达并结束返程待定状态；去程、同行人及其他人工内容不变，不新增重复回程。
9. 追问、失败或暂停后继续：草稿与引用持续存在，追问时隐藏提单卡，收集结束展示当前目标卡；恢复不重复新建，正文不复述卡片 JSON 或内部 ID。

## 交付与限制

当前员工、线路、组织仍为本地示例数据。正式接入需提供员工主数据、授权组织目录及线路/差旅政策接口。真实提交仍由用户在抽屉确认，现有本地受理状态不改称外部审批成功。住宿与 OA 智能匹配、同行代提、历史行程重叠核对不在此次默认规则的新增范围。
