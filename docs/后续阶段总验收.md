## 本轮发现并修复的问题

- 下拉框label混入option文字，导致精确标签不可用；现有明确标题关联，票据金额各有准确名称。
- 匿名401误取消身份列表、切换身份多传登录字段、测试抢在Set-Cookie完成前请求、Vite先于API启动造成代理500；均经实际浏览器定位并修复。
- 等待检查点释放租约前未累计活动耗时；现在同epoch只结算一次，等待期不累计，续接预算递减。
- 原unknown只有手动核实；现在使用持久attempt租约和退避巡检，十五分钟仍未知升级脱敏人工核查，始终只查原回执。
- 审批成功后原主管已不能再次审批，导致其原action也不可读；回执读取现按本人账本与当前读权校验，执行仍校验原写权。
- 续接可能重放旧授权工具正文；工具调用权限快照不可变，恢复只带完成状态/action引用，业务正文重读当前领域授权。
- 上下文只计初始prompt，漏计检查点/补充/工具结果；现在计完整材料和工具schema，实际SDK每轮发送模型前再次核验70%预算。
- SDK每轮输出预算现按run剩余额度、上下文30%和16000上限共同约束；通过公开stream重新绑定有界prepared options，实际SDK测试网关验证25→15逐轮递减，不冒充真实模型验收。
- 规则启用参数可夹带disable改变真实意图；准备与执行均严格解析，未知字段拒绝，摘要与执行不再分歧。
- 草稿改名/分类曾影响旧生效版预审；0022版本元数据与读取路径现绑定真实active版本，缺可信历史元数据失败关闭。
- 公司规则发布后立刻重开编辑曾读取旧列表version，实际浏览器复现409；现在打开前GET当前规则，再按原速度保存，复杂v2发布与停用已通过定向浏览器验证。
- 人工专用测试集、明确规则停用和映射发布已补齐。真实映射发布使预审low→incomplete→low，同时保留原始财务值、失效旧结果；外部未接来源明确sample_only。
- 完整浏览器复验发现新Skill种子仍固定引用旧`finance.action.status@1.0.0`，在试运行前失败；新种子现精确引用已发布`1.1.0`，既有Skill/历史定义不改。两条红→绿回归核对全部必需依赖published/enabled、seed重入不变，验证先通过capabilities再因真实模型配置缺失明确blocked。
- 工作空间验收原来轮询列表首项，会先误读旧终态再看到新queued任务；现绑定本次POST响应的run/thread/message/owner，精确轮询同run，保留缺模型错误码及零调用断言，定向3/3通过。
- 订阅只读身份无法读取本人指派待办；现按类型/部门读权与本人指派筛选，未赋审批权限或暴露Skill源码。
- 日报测试误把业务日期当生成时间；现验证真实UTC生成时间、投递正文、来源版本和重复打开的原会话/卡片。

## 契约矛盾及本轮采用的解释

1. 原始01公共契约§5的ResourceRef固定枚举不含mapping；M11§5的动作要求是“至少覆盖”，允许在唯一动作registry登记模块需要的动作。因此新增`rule.disable`和`rule.mapping.publish`，不扩ResourceRef、不把mapping ID伪装为rule。映射使用空资源列表及单个null资源执行项，以extra_guards绑定对象、版本、草稿hash、样例proof和授权，准备/执行两次领域校验并在事务内CAS。动作状态输出正式升至`finance.action.status@1.1.0`，没有静默改写旧published协议。先前“清单固定导致无法实现”的判断已纠正，具体接线见`M03-治理补齐记录.md`。
2. M03§4明确测试999.99/1000/1000.01元及未知金额，02和03有999/1000/1001元简写。固定boundary-v1采用模块中更严格的一分边界，另有整数分解释器断言；未把未执行的整数元测试写成通过。
3. 旧T01兼容记录Node22和空seed是历史；实际dsh要求Node>=24.9，当前统一锁定24.22.1。后续完整seed/reset仅在显式Demo模式可用，production拒绝。
4. Skill种子只有合成证据，不满足真实验证+独立审查的发布门槛。它们可发现但不可假调用；旅程06走正式治理前置步骤，缺模型时blocked。
5. 业务时钟用于查询日与计划槽；发生时间、生成时间、租约、确认过期、退避与审计均用真实UTC。回拨不会延长安全期限。
6. 规则原表仅在定义上保存名称/分类，新草稿会覆写。0022将其绑定到具体版本并不可变；只对可证明的当前版本回填，归档/维护代和无可靠历史的版本保持未知并在普通读侧失败关闭，不猜测旧值或绕过Demo写屏障。

固定`boundary-v1`仍只适用于能构造四项金额边界的规则。复杂AST使用人工登记的4–100项独立预期集合，绑定租户、owner、规则及精确草稿版本/hash，经真实队列评估后才产生发布proof。仅改名的新草稿也不能复用旧集合。既有`finance.rules.test@1.0.0`保持原输入和四项proof定义；扩展HTTP schema不冒充旧工具能力。外部业务映射标记为`sample_only`，未注册真实来源适配器时不宣称线上生效。

## 运行与补验

复制启动步骤见根README；本机原生服务可用`pnpm exec tsx --conditions=development scripts/dev-services-native.ts`恢复，跨机器使用固定版本Compose。缺Docker仅阻止容器实测，未阻止原生PG/S3验证。

真实模型需要`DSH_API_KEY`、`DSH_BASE_URL`、`DSH_MODEL`、`DSH_CONTEXT_WINDOW`。配置后重启API/Worker，依次运行`pnpm test:agent:real`、受控重建后的`pnpm test:e2e`、`pnpm test:load`。前者先实际SDK工具往返，再执行八条正式API旅程；容量脚本使用独立测试租户，不重建默认环境。

生产前还需真实SSO/组织授权、真实业务/OCR/MaaS适配器、HTTPS、部署秘密、OS资源限制、多机滚动升级与异机备份恢复演练。已接适配器必须支持幂等/回执查询，缺少能力保持关闭。具体步骤见`运行与恢复手册.md`。
