# 财小智：Codex 第一轮开发提示词

## 使用方法

将本开发启动包解压到 Codex 当前项目可访问的目录。复制下面整段提示词交给 Codex。首轮范围为 `03_Codex分阶段实施计划.md` 中的 **T01 公共合同、工程与持久化基础**，不包含 T02 或 T03。

包内保留上一轮全部 19 份设计文档，正文与原版一致；本文件为新增的第 20 份文件。

## 可直接复制的提示词

```text
你现在负责“财小智”的第一轮工程开发。请在当前项目目录直接完成代码、配置和必要验证，不要只给方案。

【一、先读取设计与现有工程】

先检查当前仓库的 AGENTS.md（如有）、README、目录结构、依赖和未提交改动，再定位本次设计包。依次完整阅读：
1. 00_阅读顺序与Codex使用说明.md
2. 01_总体架构与公共契约.md
3. 02_联调验收与演示数据.md
4. 03_Codex分阶段实施计划.md

设计文件是规格依据，不是已实现代码。其他模块文件按公共契约的引用查阅。保留原始设计文件，不擅自修改业务要求；发现矛盾时记录具体位置和本轮采用的解释。

【二、本轮范围：仅执行 T01】

本轮只执行 03 文档中的“T01 公共合同、工程与持久化基础”。完成后停止，不自动进入 T02 或后续任务。

项目最终是 B/S 财务个人助理；Agent 路线固定为 dsh。Agent 核心按产品级要求建设，支撑业务系统允许简化 Demo。这是全局背景，不代表本轮实现所有模块。

本轮交付一个可运行、可继续开发的工程基础：前端、API、Worker 骨架，共享契约，数据库迁移，私有文件存储，outbox 基础，以及真实的验证记录。

【三、具体开发要求】

1. 工程与依赖
采用 TypeScript、React + Vite、Fastify、PostgreSQL + Drizzle、pnpm workspace；本地文件服务使用 S3 兼容私有对象存储。版本依据实际可安装、相互兼容的依赖确定，并固定 lockfile 和容器版本，不编造版本或 SDK 能力。

建立或适配以下结构：
- apps/web
- apps/api
- apps/worker
- packages/contracts/src/{common,events,cards}.ts
- packages/jobs：仅本轮需要的 outbox 基础
- infra/compose.yaml
- infra/migrations
- tests/contracts
- tests/integration
- docs

已有工程优先复用；保留用户代码和未提交改动，不清空重建、不做无关重构。若现有结构不适合承载新工程，在当前项目内使用独立子目录，并解释位置和启动方式。不要为了目录齐全创建全部 15 个模块的空实现。

2. 公共契约
按 01 文档建立唯一来源的 TypeScript 类型及运行时校验 schema，至少覆盖：
ActorContext、Money、ResourceRef、ActionReceipt、AgentCard、ToolResult、RunStatus、统一响应/错误，以及公共事件信封。

字段、枚举、错误码与版本规则以设计文件为准，不自创第二套协议。不同卡片 payload 在后续模块按类型补充，不把任意对象当作已完成的业务 schema。

本轮落实并测试：
- 金额用整数分字符串，币种按首期 CNY 契约处理，不能用浮点数保存金额。
- 时间存储使用 UTC，业务时区默认 Asia/Shanghai。
- 资源引用携带版本。
- 严格校验已定义 schema，拒绝非法枚举、金额格式及未知字段。
- ActorContext 是服务端可信上下文；本轮定义契约，不开放由浏览器自报身份的业务接口。
- 前端、API、Worker 复用同一公共包。

3. 持久化基础
提供 PostgreSQL 和私有对象存储的本地开发配置、持久化卷、初始化说明及可重复执行的迁移命令。

建立本轮必需的文件元数据和 outbox 表，具备设计要求的租户归属、资源版本及时间字段。提供真实事务写入能力，并用测试证明业务元数据与 outbox 事件可以同事务提交、失败同事务回滚。

实现基础文件存储适配器与私有桶配置；尚未实现鉴权时，不暴露匿名业务文件上传/下载接口。后续完整任务队列、租约调度、Agent 运行恢复和动作执行器不在本轮实现。

db:seed 仅提供本轮需要的最小技术验证数据或明确的空初始化，不提前植入完整演示业务；production 模式拒绝演示 seed/reset。

4. 最小运行链路
- Web：提供简洁中文工程状态页，通过真实 API 显示基础服务状态；不要展示虚构待办、审批结果或聊天回答。
- API：提供存活与就绪检查，能区分进程正常与数据库/文件依赖未就绪；不向页面泄露连接串、密钥或内部异常详情。
- Worker：能启动、加载环境配置、输出必要结构化日志并优雅退出；不伪装已经完成 dsh 执行。
- 配置：提供 .env.example、.gitignore，区分 demo/test/production；不要提交真实凭据。模型密钥不应成为 T01 启动的必要条件。

5. 开发命令与说明
提供并说明：
pnpm dev
pnpm build
pnpm db:migrate
pnpm db:seed
pnpm typecheck
pnpm test:unit
pnpm test:contracts
pnpm test:integration
pnpm test:e2e
pnpm test:agent:real
pnpm test:load

当前已实现的命令必须执行真实逻辑。留给后续阶段的测试命令应明确返回“未实施/未配置”，不能空跑后报告通过，也不要为凑命令提前实现后续阶段。

README 写清环境要求、配置步骤、基础服务启动、迁移、应用启动、停止方式及常见故障。记录实际依赖版本；dsh 兼容性验证明确标记为后续 T03。

【四、本轮不展开的内容】

不实现 SSO/角色登录、报销/差旅/OA/审批业务、规则与预审、Skills Hub、知识问答、数据分析、个人记忆或主动提醒；不实现完整对话与抽屉界面。

不接入真实模型或 dsh SDK，不做 Agent 框架重新选型。dsh 的真实接入、工具调用和恢复验证在 T03 实施。本轮不得用固定回复冒充 Agent 已完成。

【五、验收：以实际执行结果为准】

至少实际执行并记录：
1. 依赖安装、类型检查和构建。
2. 公共契约正反例测试，覆盖非法金额、非法枚举、未知字段及缺失资源版本。
3. 数据库迁移与重复运行检查。
4. outbox 同事务提交/回滚的集成验证。
5. 基础记录和文件在对应服务重启后仍可读取；私有文件不能匿名读取。
6. Web、API、Worker 最小启动检查；依赖未就绪时状态真实可见。

若环境缺少 Docker、数据库、对象存储或安装依赖所需网络，完成所有可以完成的代码与验证，明确列出受阻命令、原因及补验步骤。不能把未执行写成通过，也不能仅因缺少模型凭据停止 T01。

验收通过只表示 T01 完成，不表示 Agent 或整套产品已完成。

【六、工作方式与结束输出】

先给出简短的执行清单，然后直接开发；不要停在方案或等待我再说“继续”。遇到不阻塞本轮的细节，采用与设计一致的合理默认值并记录。

结束时给出：
- 本轮实际完成内容与主要文件。
- 我可以复制执行的启动命令。
- 已执行检查及结果，未执行检查及原因。
- 当前限制、必要配置和遗留问题。
- 一段简短的 T02 前置条件说明，但不要开始 T02。

现在开始，只完成 T01。
```
